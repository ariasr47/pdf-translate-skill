## The finding: `center` on a left-aligned label

It put `Signature of parent or guardian` and `Date` in `center`. Both are
left-aligned in the source, flush with the signature rules beneath them.

| | original x0 | output x0 |
|---|---|---|
| Signature caption | 72.0 (flush with the rule at 72) | **64.5** |
| Date caption | 360.0 (flush with the rule at 360) | **357.2** |

The Spanish caption is wider than the English, so centring on the original
midpoint pushes it out **both** sides: it now overhangs the left end of the
rule it belongs to by 7.5 pt, which is plainly visible at reading size.

Every gate passes. Field parity, ink ratio, placement, identifiers,
canonical text layer, document metadata — all green, because none of them
knows what a caption is anchored to.

**The skill invited it.** `references/translations-format.md` says `center`
is for *"column headers, titles, signature captions"*. A signature caption
under a rule is the one place the example is wrong: it is left-anchored, not
centred. The model followed the documentation and got a worse page.

**Closed as row 18, 2 September.** Example corrected, `SKILL.md` step 5
says it, `test_center_moves_a_left_flush_caption_off_its_rule` locks the
geometry (a wider translation `center`ed lands at x0 57.67 against a rule
at 72; anchored left, at 72.0; verify passes both). Response 2 below was
decided against — see the brief's closing note.

This is a silent-PASS class of exactly the kind the program waits for, and
it came from a model rather than from someone inventing a gate. Two
responses, in order:

1. **The example is a defect.** Fix it: `center` is for a run whose source
   is centred in its own box, not for one flush with a rule.
2. **A possible warning, for its own sitting.** A `center`ed run that ends
   up wider than the source bbox now covers space the source did not. For a
   real centred title that is correct and wanted, so this is a warning at
   most — never a gate. Do not build it today.
