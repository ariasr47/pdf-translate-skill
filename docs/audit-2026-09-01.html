Verdict

This is an unusually disciplined skill. Strip-and-retypeset at the content-stream level, field identity as a hard invariant, ten automated gates, 57 constructed-fixture tests, a corpus with recorded verdicts, and a refusal-first philosophy. The bakeoff evidence that prose moved model behaviour across three vendors is rare and valuable. Nothing in the comparable open-source skills handles fillable forms at all.

But the gates still pass wrong output in classes the skill claims to cover. Arabic and Devanagari are drawn with unjoined letterforms while the docs and tests say shaping works. OCR'd scans, the exact input the skill tells users to produce, get double-printed and pass every gate. Any non-Latin source language makes the leak gate fail correct output. Rotated labels are laid flat, nested XObject text survives stripping, and widget text (tooltips, dropdown options, default values) is either never translated or mis-extracted.

Strategically, it is a form localizer, not yet the document translator its description promises. The per-line, hand-declared-merge model does not scale to manuals or brochures, and there is no translation-quality layer at all: no linguistic QA checks, no reviewer step, no way to accept an issuer's glossary. That is where BabelDOC, DeepL, and professional practice (ISO 17100, the Judicial Council's own protocol) invest most.

Found and fixed on the way

  • /ActualText never reached Story output. The wrapper looked for BT…ET, but insert_htmlbox draws into a Form XObject and appends only q /fzFrmN Do Q; RTL merges therefore carried no logical text. The span now wraps the invocation stream (gate 16).
  • Backslashes in CSS font paths. MuPDF's CSS parser eats them, so a Windows path in @font-face silently fell back to a font without the target script; merges were affected too. CSS gets POSIX paths now (gate 16).
  • pikepdf normalises page inheritance. It pushes inherited attributes onto pages on open and on save, so an inherited-resources fixture has to be built with PyMuPDF xref surgery; the /Parent walk in strip is a safety net and the leftover-text gate is the proof (gate 13).
  • PyMuPDF's show_pdf_page nests two XObject levels per shown page, which is why the old one-level walker missed even a single letterhead (gate 13).
  • The fill round-trip gate failed every form without a text field. A checkbox-only fixture built for program row 11 exposed it: the gate looked for a text widget to fill and treated "none found" as a failure instead of "nothing to check". Consent sheets and questionnaires with only tick boxes could never pass verify. Fixed with a regression test in the row-11 commit.
  • The suite was green because of a gitignored font. Syncing the plugin copy exposed it: find_test_font() preferred a Noto file under work/; anywhere else it fell back to Arial, whose cmap makes MuPDF report a soft hyphen (U+00AD) for W-2, and three placement and identifier tests failed. This is finding H4 surfacing in the repo's own tests. The fold now covers U+00AD, system fonts come first, and the installed copy passes all 78 tests (commit after 66790fa).

What is strong

Keep these. Several are genuinely ahead of everything else surveyed.

Field identity as the top priority

Every comparable tool either ignores AcroForms or destroys them (one popular skill uses redaction annotations, which delete widgets). This skill keeps 266 fields byte-identical and proves it with a gate.

Refusal is a product

Scan detection, the 0.7× overflow gate, null scaffolds that refuse to ship, and "a green verify on an untranslated file is worse than a halt" are the right instincts for legal and medical documents.

Write/find/say

A crisp, teachable rule for identifiers (Schedule C, quoted attachment labels, paper sizes, currency) that the bakeoff showed propagates through prose to models never tested. It matches the NCSC and Judicial Council guidance almost exactly.

Identity record and issuer lookup

Class, issuer, parallel text, identifiers, recorded before translating. This is ISO 17100 "reference material" done as an agent habit, without a shipped dictionary.

The gate-is-the-bug loop

Constructed fixtures, one gate per session, "gates pass and output is wrong means the gate is the bug". The program docs are a better skill-development methodology than most published guidance.

Provider neutrality with evidence

Seven scripts, no SDK, and a bakeoff across Anthropic, xAI and OpenAI models with a shared rubric calibrated to an approved reference rather than to zero.

Verified defects

Each item was reproduced by driving the shipped scripts on a constructed PDF (scratchpad probes, listed under Method). Severity reflects "silent pass" risk: how confidently the pipeline ships wrong output.

C1CriticalFixed · gate 16Verified · render + code points

Arabic and Devanagari are drawn without shaping; the docs and tests say the opposite

Every non-merge run goes through TextWriter.append. MuPDF's TextWriter does no complex-script shaping: Arabic letters come out as isolated presentation forms, and Devanagari conjuncts are drawn as consonant + halant sequences. PyMuPDF's own recipes say TextWriter and insert_text must not be used for these scripts and point at the HarfBuzz-backed Story engine, which insert_htmlbox already uses for merges.

Evidence
TextWriter   السلام عليكم  → chars FE8D FEDD FEB1 FEDD FE8D FEE1 (all ISOLATED forms)
insert_htmlbox              → chars FE8D FEDF FEB3 FEFC (initial/medial forms + lam-alef ligature)
Devanagari   क्षत्रिय       → TextWriter draws क् + ष and त् + र separately; htmlbox draws क्ष and त्र
Why the gates miss it

verify --translations reads the logical string back from /ActualText, so placement passes; ink density barely moves; RtlTextLayerTests only assert the round-trip. EDGE_CASE_FINDINGS.md ("shaping demonstrably works"), fonts.md ("MuPDF's TextWriter joins Arabic letters") and goal 04 all rest on a render nobody checked at the glyph level.

Fix

Route any run whose target script needs shaping (Arabic, Syriac, N'Ko, every Indic script, Khmer, Myanmar) through the Story engine: an insert_htmlbox per line with the same rect, size and colour, or Story with a one-line layout. Add a glyph-form gate: for Arabic targets, extract rawdict chars and FAIL if joining letters come back as isolated forms; for Indic, compare against a HarfBuzz reference render. Rewrite the RTL and complex-script paragraphs in fonts.md and failure-modes.md.

C2CriticalFixed · gate 14Verified · probe P8

An OCR'd scan passes every gate and ships double-printed

The skill refuses image-only pages and tells the user to "OCR first". An OCR'd PDF is an image plus an invisible text layer (render mode 3). That text is extractable, so the refusal never fires; strip removes the invisible text; retypeset draws the translation on top of the scanned pixels, which still show the source language.

Evidence
extract: 0 warnings, unextractable pages []      retypeset: rc 0
ink ratio translated/original = 2.13  (verify ceiling is 3.0 → PASS)
Fix

Detect invisible text (render mode 3/7) and text whose bbox sits on an image; refuse with a message that names the real requirement ("this is a scan with an OCR layer; translation needs a masking mode"). Then decide whether to offer an explicit, opt-in masking mode (white boxes under each line, which BabelDOC ships as --ocr-workaround), clearly labelled as lower fidelity. Add a gate: after strip, the ink inside the original text bboxes must drop; if it does not, the glyphs were pixels.

C3CriticalFixed · gate 15Verified · JA→EN probe

The leak gate is inverted for every non-Latin source language

The leak scan looks for Latin words ([A-Za-z]{4,}). For a Japanese, Chinese, Arabic, Russian or Greek source translated into English or Spanish, the translation is what the regex matches. --source-words-from does not help: it harvests Latin tokens from the source segments, finds none, and silently falls back to the same regex.

Evidence
JA source → EN target, correct output:
  default flags        → FAIL untranslated running text: "Income and Expense Declaration / Name"
  --source-words-from  → "leak scan: 0 source words" then the same FAIL
  --translations       → same FAIL
Fix

Make the leak scan script-aware: detect the dominant Unicode script of the source segments (unicodedata or the regex module's \p{Script}), scan the output for runs of that script, and for spaceless scripts use n-gram containment of the original segment strings instead of whitespace words. Add a JA→EN and AR→EN fixture to the corpus with verdict translate. The description says "any language to any language"; today verify only agrees when the source is Latin.

H1HighOpen · re-checked 2 SepVerified · probe P2

Rotated text lines are re-typeset horizontally

The extractor keeps origin, bbox and size but not the line direction. A label written at 90° (spine text, vertical table headers, "FOR OFFICE USE ONLY" stamps) is placed flat at its origin, across whatever was beside it. Page-level /Rotate is fine (probe P1: origins identical in unrotated space); this is about line["dir"].

Evidence
source line  dir (0.0, -1.0) origin (300, 500) bbox [287, 388, 304, 500]
output line  dir (1.0,  0.0) origin (300, 500)
Fix

Record dir per segment; in retypeset use TextWriter.write_text(morph=(origin, Matrix(angle))), which PyMuPDF documents for exactly this; compute the width budget along the line direction. Add corpus/rotated_text.pdf, distinct from the existing rotated.pdf (which only tests page rotation).

H2HighOpen · next gateVerified · probes P3, P10

Widget appearance text leaks into extraction; tooltips and dropdown options are never translated

get_text() includes annotation appearance streams. A text field's default value and a combo box's current value therefore appear in to_translate.json as if they were page text, get translated, and are drawn underneath the widget, whose appearance still shows the source value. Meanwhile the field tooltip (/TU, shown on hover and read by screen readers), the other /Opt choices, and /DV defaults are never extracted, so they cannot be translated.

Evidence
cores: ['Applicant information', 'Not applicable', 'Single']   ← the last two are widget /AP text
'/TU' "Enter your full legal name" in cores? False     'Married' (an /Opt choice) in cores? False
page.get_displaylist(annots=False).get_textpage()  → 'Applicant information'   (clean)
Fix

Extract page text from an annotation-free display list (verified to work) or from a pikepdf copy with /Annots removed. Add a "widget text" channel to the mapping, next to --captions: tooltips, choice display strings (keep export values), default values. Gate: output /Opt export values and /V semantics identical; display strings translated or declared.

H3HighFixed · gate 13Verified · probe P4

Text inside nested Form XObjects and under inherited resources survives strip, silently

strip_text.py only walks XObjects listed in the page's own /Resources, one level deep. A Form XObject inside a Form XObject (letterheads, imposed pages, anything built with show_pdf_page) keeps its text; a page whose /Resources are inherited from the /Pages node keeps all XObject text, and the strip report says form_xobjects_stripped: []. Extraction sees that text, so the translation is drawn on top of surviving source text.

Evidence
nested:    text left after strip → 'INNER XOBJECT TEXT\nMID TEXT'
inherited: text left after strip → 'PAGE TEXT\nINNER XOBJECT TEXT\nMID TEXT'   report: []
Fix

Recurse into XObject resources with a visited set; resolve inherited resources by walking /Parent (pikepdf's page.get('/Resources') does not inherit). Add the cheapest gate in the system: after strip, get_text() of the stripped file must be empty except widget text. That single check would have caught both cases.

H4HighOpen · re-checked 2 SepVerified · probe P12, codepoint study

Text-layer code-point drift: the NBSP and hyphen folds in verify are symptoms of one root cause

MuPDF builds each embedded font's ToUnicode by reverse-mapping the font's cmap. When several code points share a glyph, the wrong one can be reported: spaces as U+00A0, hyphens as U+00AD, and common kanji as CJK Compatibility Ideographs (立→U+F9F7, 年→U+F98E, 行→U+FA08, 見→U+FA0A, 金→U+F90A, 料→U+F9BE). With the full Noto Sans JP font, verify --translations fails a correct 申立人 sentence. Subsetting masks it because the duplicate code points are dropped from the cmap (confirmed: the four FL-150 outputs contain zero drifted characters, and the subset path yields clean U+0020/U+002D). It is real for field_fonts.py, which embeds the full font, for anyone who takes the documented option to skip subsetting, and for the repo's own tests, which is why the folds exist.

Evidence
full Noto Sans JP:  '申立人は…' → extracted 申U+F9F7人…  → FAIL missing translation targets
full Arial:         spaces → U+00A0 (19/19), '-' → U+00AD soft hyphen
subset via prepare_font: 'Nombre del solicitante…' → 0 NBSP, hyphens U+002D
Fix

Post-process the output's ToUnicode CMaps with pikepdf to prefer the authored code points (canonical over compatibility, U+0020 over U+00A0), or emit /ActualText per run as the RTL path already does. Add a "canonical text layer" gate: no U+F900–FAFF / U+2F800–2FA1F, NBSP or soft hyphen unless authored. Then the NBSP and U+2010 folds can go.

M1MediumOpen · re-checked 2 SepVerified · probe P7

Right-aligned text is re-anchored to the left

Only center exists. A right-aligned label or column header grows rightward from its original left edge, past the original right edge, until it hits an obstacle. Amount columns, "Page 1 of 4" footers and right-set headers all drift.

'Total' right edge 540.0 → 'Gesamt' bbox x1 = 555.3
Fix

Add a right list (mirror of center), and let the extractor propose it: segments whose right edges align across rows while left edges do not.

M2MediumOpen · re-checked 2 SepVerified · probe P7

Italic, serif and mixed inline styles are dropped

The extractor records italic, but retypeset has only regular and bold slots and one family for the whole document. Times Italic becomes upright Arial; a serif body becomes sans; a line with a bold word in the middle can only be expressed with the ‖ bold-lead-in trick.

Fix

Font roles (regular, bold, italic, bolditalic) per family (serif, sans, mono) selected from PyMuPDF span flags (bit 1 italic, bit 2 serifed, bit 3 mono, bit 4 bold); accept <b>/<i> markup in single-line targets the way merges already do.

M3MediumOpen · re-checked 2 SepVerified · probes P6, P11

Encryption is silently dropped; Adobe usage-rights signatures ship invalid

An encrypted source (the corpus has one) comes out of both pikepdf and ez_save unencrypted, with any owner-password restrictions removed and no message. FL-150 carries /Perms /UR3, an Adobe Reader-extensions signature; the outputs still carry it although the content changed, which is what makes Adobe Reader show the "extended features are no longer available" banner. No bakeoff run was opened in Acrobat (the notes say so).

Fix

Recon reports encryption, permissions and /Perms or DocMDP certification; strip deletes /Perms (the signature cannot survive editing) and says so in the report; optional --keep-encryption re-encrypts with the original permissions; certified (DocMDP) documents get a warning in the deliverable.

M4MediumOpen · re-checked 2 SepVerified · probe P5

Output metadata still describes the English document

Every FL-150 output keeps /Lang en-US, the English /Title, and a /StructTreeRoot whose tags point at content that no longer exists, with /MarkInfo /Marked true still claiming an accessible PDF. Screen readers announce the wrong language and read an empty structure; WCAG technique PDF16 expects /Lang to match the document language.

Fix

Set /Lang to the target BCP-47 tag and XMP dc:language; treat /Title as a core; translate outline titles (get_toc/set_toc); remove the orphaned structure tree and set Marked false until tags can be rebuilt; say in the deliverable that accessibility tags were removed.

M5MediumOpen · code unchangedVerified · JA→EN probe

No per-character glyph coverage check at retypeset

When the chosen font lacks a glyph, MuPDF substitutes its built-in fallback font mid-string, and when that also lacks it, draws a box. Japanese placed with Arial rendered in a different typeface, with 立 as a box, and retypeset returned 0. prepare_font's rasterization assert samples at most twelve characters.

Fix

In retypeset, check font.has_glyph for every character of every placed run against the exact font object and FAIL listing the characters. It is a five-line gate that closes a silent class.

Gaps against best practice

Not defects in the code; things the field does that the skill does not, ordered by how much they would change outcomes.

1. A translation-quality layer (the largest gap)

The program rightly refuses to ship a terminology dictionary. It then treats every other quality mechanism as if it were one. Three things professional practice adds are provider-neutral and glossary-free:

  • Linguistic QA checks of the Xbench/Verifika class, run on translations.json: numbers and dates that vanish or change, targets identical to source for non-identifier cores, the same source string mapped to different targets (case or punctuation variants), unpaired brackets and quotes, trailing colon and punctuation parity, doubled spaces, and length-ratio outliers against a real expansion table. None of this judges meaning; all of it catches the class of error the bakeoff found (the dropped d., the empty target, the English rev line) before a human looks.
  • A reviser step. ISO 17100 requires revision by a second person; the Judicial Council protocol requires a reviewer who "must compare the source text with the translation" and says machine translation "should not be used as the sole mechanism" without a disclaimer in the user's language. The skill mentions a second linguist once, in RECOMMENDATIONS.md; the Deliver step does not require a review record. An LLM-as-judge pass with an MQM error typology (GEMBA-MQM shows span-level, reference-free quality estimation works) can be shipped as a prompt template plus JSON schema, run by any model, and attached as review.json. It is not a glossary and it does not launder a weak author; it is the reviser step made explicit, with the human still named for official work.
  • Job-level glossaries as input, never shipped. The issuer's published terms, a client termbase, or the Judicial Council's own glossaries are exactly what the identity record tells the author to look up. BabelDOC accepts --glossary-files and auto-extracts terms for cross-page consistency. A glossary.csv job input with a consistency gate (source term present, target term present) keeps the "no dictionary in the repo" rule and closes the "養子支援 next to 養育費" class as far as tooling can.

2. Compliance and delivery for official documents

  • California courts state that translated Judicial Council forms are for reference and that filings must be in English; the NCSC guide says translated forms should carry an informational-only notice. The skill produces a Japanese FL-150 that looks fileable and says nothing. Make a target-language notice a required deliverable for court and government classes, decided at the identity step.
  • USCIS (8 CFR 103.2(b)(3)) requires a full English translation plus the translator's certification of completeness, accuracy and competence for foreign-language documents. Ship a certification statement template that a human signs; state plainly in SKILL.md that the skill produces a working copy, not a certified translation (this sentence already exists in RECOMMENDATIONS.md, where no agent reads it).

3. Long documents and paragraphs

BabelDOC parses pages into a paragraph-level intermediate representation, reflows translations with an iterative scale search, extracts terms for consistency, and emits bilingual output; DeepL ranks layout constraints (page boundary, element position, relative size, absolute size) and tunes font size per element in half-point steps. The skill's line-plus-hand-declared-merges model is the right choice for forms and the wrong one for the manuals and brochures the description promises. Add a paragraph mode that turns PyMuPDF block groupings into merge proposals the author accepts in bulk (never silently), reuse the scale search from merges, partition work by page, and offer a bilingual (alternating pages) output, which every pdf2zh user expects.

4. Expansion guidance is wrong for the documents this skill is for

SKILL.md says EN→DE grows about 30%. That is the paragraph figure. The W3C/IBM table gives 200–300% for strings under ten characters, 180–200% for 11–20, and only 130% above 70; Thai needs about 150% of the vertical space. Forms are made of short labels. Put the table in the skill and make the extractor's length warnings use it.

5. Untranslatable surfaces the skill does not enumerate

  • Raster images that contain text (agency banners, stamps, logos) and text converted to outlines pass every gate on a born-digital page. List image regions per page as review items; the description promises brochures, where this is the norm.
  • Outline titles, page labels, link and annotation /Contents, FreeText annotations, document /Subject and /Keywords, JavaScript alert strings.
  • Choice fields: field_fonts.py rewrites /DA only for text fields, so a dropdown's selected CJK value can still render in a Latin fallback.
  • Vertical CJK (tategaki), Thai dictionary line-breaking inside merges, mixed-script fallback within one run.

6. Fonts

prepare_font.py subsets and embeds whatever TTF it is given; the tests use Arial. Read OS/2.fsType and refuse restricted-embedding fonts (value 2) and warn on the no-subsetting bit (0x0100); recommend Noto (OFL) by default, which fonts.md already does for CJK.

Frontmatter and structure

  • Valid: kebab-case name matching the directory, 804 of 1,024 description characters, only allowed keys, 318 body lines (guideline: under 500), references one level deep.
  • Missing optional fields worth adding: license (there is no LICENSE file anywhere in the repo, which undercuts "a public skill"), compatibility (Python 3.10+, pymupdf/pikepdf/fonttools, internet access to fetch Noto fonts, an image-viewing harness), metadata: version.
  • The description mixes triggers with mechanics ("strip-and-retypeset pipeline (never overlay, never redaction) with bundled scripts for…"). Anthropic's guide wants what-plus-when; the writing-skills testing found that workflow summaries in descriptions get followed instead of the body. Keep the rich triggers, move the mechanics into the body where the invariants already live.
  • The opening italic paragraph ("The YAML block above is optional metadata…") is for humans reading the file on GitHub, not for the agent that loads it. Move it to the README.

Body

  • 2,300 words is heavy for a body that is loaded whole. Write/find/say is explained in step 3, again in step 6, again in translations-format.md, and in failure-modes.md; the --translations gate is described in three paragraphs of step 6. The repo's own rule is "one home per fact". Consolidate, then add the Anthropic-style copyable checklist (recon → identity → strip → extract → author → font → rebuild → render → gates → field fonts → deliver with notice) so the sequence is trackable.
  • The tone is right: reasons, not shouting; concrete failure classes; honest limits. Keep that. Two claims need correcting after this review: "shaping works" for Arabic, and "EN→DE grows ~30%".
  • Degrees of freedom are well chosen: exact commands for the fragile pipeline, judgment for language. The one place freedom is too high is delivery: the report format is prose guidance where a template (identity facts, structural changes, compressed translations, locale adaptations, review status, notice) would give a checkable shape.

Testing discipline

  • The goal loop is close to the writing-skills method: baseline (bakeoff v1), change the prose, re-measure (v2). That is the strongest evidence in the repo and should be kept as a first-class asset, but the bakeoff harness lives in three duplicated copies (bakeoff/, Claude Session Handover/, runs/claude-handover/) plus a damaged zip.
  • Tests depend on system fonts (Arial on Windows, DejaVu on Linux) and skip RTL when none has both scripts. Vendoring one OFL font (Noto Sans, Noto Naskh Arabic subset) would make the suite deterministic and unlock CI, which does not exist.
  • Packaging: goals/, three session prompts and four HTML explainers (about 210 KB) sit inside the skill directory and ship with it. Move development material to a repo-level dev/; keep corpus/ and tests/ with the skill.
  • requirements.txt has no upper bounds. PyMuPDF changes surfaces between minors (a display-list text page needed manual wrapping today); pin a tested range and record it in compatibility.

Method and sources

What was done

  • Read every file in pdf-translate/ (skill, references, nine scripts, both test modules, corpus, goals 01–12, program, recommendations, handover, implementation), the root notes, the bakeoff harness and results, and one competing model's run notes.
  • Ran the shipped suite: 57 tests pass in 14 s on Python 3.14.0, PyMuPDF 1.28.0, pikepdf 10.12.0, fontTools 4.63.0 (Windows 11).
  • Fifteen probes driving the shipped strip_text, extract_segments, retypeset, prepare_font and verify on constructed PDFs: page rotation, rotated text lines, widget tooltips/options/values, nested and inherited XObjects, metadata and tags, encryption, italic/serif/right alignment, an OCR'd scan, Arabic/Hebrew/Thai/Devanagari shaping via TextWriter versus Story, a JA→EN job through all verify modes, a code-point round-trip study with full and subset fonts, usage-rights signatures, and the text layer of four real FL-150 outputs. Probe scripts and renders are in the session scratchpad.
  • Compared the installed plugin copy with the repository (it is v1).
  • Limits: no Acrobat available, so the usage-rights banner and NeedAppearances rendering are inferred from structure; glyph-form judgments rest on code points and renders, not on a native reader; Windows system fonts (Arial, Nirmala UI, Leelawadee UI) plus the repo's Noto Sans JP were used.
