Decide before the plan
Three questions
Everything else on this canvas is settled by measurement. These are judgement.
Question 1 — the biggest
Row 32 or E3 first?
Row 32 is the repo’s P0 and its plan is written. But its plan commits to run_review() returning a ReviewVerdict that mirrors QAVerdict and VerifyVerdict — and E3 changes what that family looks like: a schema envelope, no printing, a logger.
C
Neither — row 32 builds against this canvas
recommended
The ordering conflict is not real once the family is designed, which is what this canvas does. Row 32 writes ReviewVerdict to the shape settled here — frozen dataclass, tuple fields, to_dict() with schema and version, logs rather than prints — and E3 then finds one stage already compliant instead of one stage to redo.
Cost: one edit to row 32’s plan before it is executed, adding the envelope and the logger to Task 1’s interfaces. Ten minutes, and it has to happen before the build starts, not after.
A
Row 32 first, as the handover says
Honours the stated order. A wrong term of art reaching a delivery is the open hole; E3 is readiness work for someone else’s deadline.
Cost: review.py is written twice — once to today’s convention, once to E3’s — unless option C’s edit is made anyway, at which point A is C.
B
E3 first
Row 32 then inherits a finished surface with nothing to anticipate.
Cost: weeks, not days — see Question 3 — with the terminology hole open throughout. The product’s own order puts E3 after E2, which is done; it never asked for E3 ahead of the repo’s own P0.
Question 2
Break scale_report.json now, or leave it?
It is a bare JSON list, so there is nowhere to put schema without changing the file’s top-level type. C3 wants every output schema-versioned.
today [ {page, ratio, key}, … ] proposed {"schema": 1, "version": "57", "runs": [ … ]}
A
Break it now, in E3
recommended
Nothing outside this repo reads it yet — the product has not pinned a version and has no goldens on it. The cost is a one-line note in the release and a docs edit. After they pin, the same change costs them a migration.
B
Leave the file; return the data instead
No break at all: the runs come back in RetypesetResult, and a consumer that wants them schema-versioned reads the object, not the file.
Cost: C3 says a consumer explains every outcome from these files alone. One file stays outside that promise, and the asymmetry has to be documented forever.
Question 3
E3 is bigger than “about a week”.
The product accepted E3 at “about a week”. Sized against the measurement on this canvas:
logging move, 141 sites + parity runner ~2 d result family, 6 types + envelopes ~1 d typed exceptions, audit + family ~1.5 d progress and cancellation ~0.5 d C7 probe, then whatever it finds 1–2 d, unknown until probed Archive root + concurrency test ~0.5 d consumer guide ~1 d tests/test_consumer_contract.py ~1 d —————— 8.5–9.5 d
A
Move C7 to E8, ship the rest as E3
recommended
E8 is “performance and determinism as a published number” and its acceptance already reads “the C7 determinism test gates”. Determinism belongs there by the product’s own text, and it is the one item whose size is unknown until a probe runs. Without it E3 is 7.5 days — within sight of the accepted estimate, and with no unknown left in the total.
Needs telling the product, since C7 is listed against E3 today. One line in the requests doc.
B
Ship all of it, tell them two weeks
One coherent surface, delivered once, nothing split across epics.
Cost: it doubles an estimate the product is planning a council around, and C7’s size is still a guess until the probe runs.
C
E3a now, E3b after
C1, C3, C10, the guide and the contract test in one week; C4, C5, C7 in a second pass.
Cost: C4 and C5 are half a day each and fall out of work E3a does anyway — splitting them out costs more in ceremony than it saves.
