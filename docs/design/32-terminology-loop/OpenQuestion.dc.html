Decide before the plan
Three questions the brief does not answer
Each one came out of measuring the real job and the real source, not out of reading the brief.
Question 1
Where does finish find review.json?
Every other command that knows about a job takes --work DIR. finish does not — five bare positionals, and it never sees the work directory:
def cmd_finish(argv): orig, out, font, final, html = argv[0], argv[1], argv[2], argv[3], argv[4]
pdf_translate/pipeline.py:359 — unchanged since the command existed.
A
Add --work DIR to finish
recommended
Explicit, and the vocabulary qa, rebuild, init and the new review already use.
Cost: every existing caller adds it, and the no-flag case must refuse too, naming the missing flag.
B
Look beside FINAL.pdf
No new flag, nothing for a caller to learn.
Cost: wrong in the normal case — the FL-150 delivery went to Downloads/ while the job lived elsewhere. The gate would refuse a reviewed job, then get switched off.
C
A sidecar written by rebuild
The command that does know the work directory records it next to OUT.pdf.
Cost: a new stale-file problem of exactly the kind PR #7 was opened to fix, and it breaks whenever someone runs retypeset directly.
Question 2
The gate needs an enum. The one real review.json holds prose.
§4 of references/review.md specifies resolution: accepted|rejected|open. The FL-150 job — the very file the brief’s §4 Proof re-runs — stores sentences there:
"resolution": "accepted, applied in v2 (2026-09-17)" "resolution": "rejected: both renderings are attested; Japanese legal reference works use 上位裁判所, the press 上級; kept 上位" "resolution": "accepted with a different fix"
Nothing read it before, so nothing enforced it. A strict parser refuses all 31 findings on the only job that exists.
A
Enum in resolution, prose moves to resolution_note
recommended
Strict field, and the rationale keeps a home — it is the most valuable part of a rejection. --ingest still accepts a legacy prose value by its leading token and prints one migration line per finding.
B
Parse the leading token, keep the prose
No schema change, no migration.
Cost: “accepted with a different fix” parses as accepted and its qualification is invisible to every later reader.
Question 3
A termbase holds terms. Findings are keyed by whole sentences.
Bar item 4 says --ingest appends each accepted terminology finding as (source term, target term). But core is the mapping key, and six of the FL-150’s eleven accepted terminology findings are keyed to a sentence:
core: "Utilities (gas, electric, water, trash)" target: 光熱費（ガス、電気、水道、ごみ） suggestion: 水道光熱費（ガス、電気、水道、ごみ）
The term is Utilities → 水道光熱費. Nothing in the finding says so.
A
The reviser names the term
recommended
Two optional fields on a terminology finding, term and term_target, asked for by review_prompt.md. A finding without them is reported and skipped, never guessed into the termbase.
B
Diff target against suggestion
Mechanical, no schema change. The changed span gives the target side exactly: 光熱費 → 水道光熱費.
Cost: it cannot recover the source side, which is the column qa_check --glossary actually matches on. Good as a fallback that fills the target, never alone.
