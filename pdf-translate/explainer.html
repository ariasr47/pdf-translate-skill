Direct answer

The skill file pdf-translate/SKILL.md is the workflow. It was edited in place. The README was edited with it. The scripts the skill tells you to run were made import-safe, Windows-safe, and language-pair-general. Regression tests now live at tests/test_pipeline.py.

Unchanged on purpose: strip-and-retypeset. Text is still deleted at BT/ET, never by overlay or redaction. Graphics stay. Fields stay. A missing translation still fails the build. The visual pass is still mandatory.

What the skill now says that it did not

The old skill already described the pipeline well. It still used FL-150 and Japanese as the running example, and the comparison HTML still shipped with lang="ja". The update makes the contract explicit: any harness, any mapping author, any born-digital pair.

Was implied

Workflow written so an agent could follow it. Comparison page hardcoded Japanese. pyftsubset “must be on PATH.” Button chrome: hide and redraw, which can change the field count.

No in-repo tests named in the skill. Same-script leak scan still used a Latin-word regex that flags Spanish as “untranslated English.”

Now written

Scripts are provider-neutral: no vendor SDK, no named harness. Translation is a JSON mapping any person or model can author. Invariants are listed: field identity, no redaction, graphics untouched, glyf fonts, coverage is a hard fail.

--captions rewrites pushbutton /MK /CA in place and drops stale /AP. Extractor warns on write/find/say candidates and possible wraps — it still never auto-merges. Tests: python3 -m unittest tests.test_pipeline -v.

The seven stages are the same names, in the same order. What changed is what they assume about the environment and the language pair.

  1. strip_text + captions, XFA off, q/Q wrap
  2. extract_segments + write/find/say warnings
  3. prepare_font finds pyftsubset itself
  4. retypeset still fails loud on missing cores
  5. verify source-word leak scan
  6. field_fonts Windows temp lock ignored
  7. compare --lang, no Hiragino stack

Fixes — defects that already existed

These are not new features. They are things that failed silently or only on this machine, then got a test so they cannot slip back.

MarkFileWhat was wrongWhat happens now
Fix field_fonts.py Read sys.argv at import, so any test harness crashed. After a good save, Windows WinError 32 on the temp file failed the run anyway. Documents were left open, which caused the lock. Callable field_fonts() / main(argv). Files are closed. A lock on the temp file after a successful write is non-fatal.
Fix compare.py Same import-time argv. HTML lang="ja" and a Hiragino / Noto Sans JP font stack on every job. Callable compare(). Default lang="en", generic system sans, optional --lang and --labels.
Fix prepare_font.py pyftsubset invoked as a bare command. On this Windows install it is not on PATH; it lives under the interpreter’s Scripts folder. Search PATH, then Scripts/pyftsubset.exe next to Python, then python -m fontTools.subset.
Fix verify.py Three consecutive Latin words always failed. English→Spanish therefore failed on the translation itself. Fill round-trip wrote _verify_fill.pdf into the current directory. With --source-words-from, both running-text and isolated-token scans use this document’s source words. Fill uses a temp file.
Fix strip_text.py Rewriting a button caption left the old appearance stream. Viewers and get_text() still saw English (“Print this form”) on top of the new /CA. --captions writes /MK /CA and deletes /AP so NeedAppearances can rebuild. Field count stays 266 on FL-150.
Fix *.py JSON I/O Opens without encoding='utf-8'. Fine on UTF-8 locales; a defect on Windows when translations are not Latin-1. UTF-8 on the mapping and segment files.

New behavior the skill now documents

MarkFileWhat you get

Add strip_text.py --captions captions.json: in-place pushbutton rewrite. Prefer this over hide-and-redraw when the widget should remain.

Doc SKILL.md / README.md Provider-neutral contract, invariants, caption rewrite, extractor warnings, font-tool discovery, --lang, unittest command. FL-150 remains an example in the verbatim section, not a branch in the scripts.

What was actually run

Not a native-reader quality claim. These are the gates that passed on this pass.

Both live CLI launches printed PASS field parity, PASS fill round-trip, PASS page 1 ink ratio, PASS no untranslated running text. Extracted output contained the Spanish targets and not the English source sentence. FL-150 replay with --captions also passed field, fill, ink, and leak gates.

What this pass did not claim

The north star is still unbounded. This sheet is not a proof of “any PDF, any language pair.” Explicitly still out:

  • OCR / scanned pages
  • RTL and vertical shaping (the skill still halts if you cannot verify)
  • Rebuilding tagged-PDF /StructTreeRoot
  • Auto-merging paragraph lines by geometry
  • A translation API, a web UI, or a named vendor client
  • Native-reader indistinguishability — that is the mapping author’s job, plus the visual pass

How to run what changed

cd pdf-translate
python3 -m unittest tests.test_pipeline -v

python3 scripts/strip_text.py original.pdf stripped.pdf --captions captions.json
python3 scripts/extract_segments.py original.pdf
python3 scripts/prepare_font.py FONT.ttf translations.json font-sub.ttf
python3 scripts/retypeset.py stripped.pdf segments.json translations.json out.pdf
python3 scripts/verify.py original.pdf out.pdf --source-words-from segments.json
python3 scripts/field_fonts.py out.pdf FULL_FONT.ttf final.pdf
python3 scripts/compare.py original.pdf final.pdf comparison.html --lang es
